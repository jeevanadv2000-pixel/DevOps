## 1. The six important Terraform blocks

The session begins by revisiting six important Terraform configuration blocks.

| Block      | Purpose                            | Main question it answers                       |
| ---------- | ---------------------------------- | ---------------------------------------------- |
| `provider` | Connects Terraform to a platform   | Where will Terraform manage resources?         |
| `resource` | Creates and manages infrastructure | What do we want to create?                     |
| `variable` | Accepts input values               | What values can the user customize?            |
| `output`   | Exposes useful information         | What information should Terraform display?     |
| `locals`   | Defines reusable expressions       | What calculated or common values can we reuse? |
| `data`     | Reads existing information         | What information should Terraform look up?     |

The most important block is `resource`, because that is where we declare the infrastructure Terraform should manage. The other blocks support resource creation, configuration reuse and information retrieval.&#x20;

### 1.1 Provider block

A provider is a plugin that allows Terraform to communicate with an external platform through its APIs.

Examples:

- AWS provider
- AzureRM provider
- Google Cloud provider
- Kubernetes provider
- GitHub provider

Example:

```
provider "aws" {
  region = "ap-south-1"
}
```

This tells Terraform to use the AWS provider and configure it for the Mumbai region.

Remember: A provider is not the cloud resource itself. It is the integration that allows Terraform to manage resources on that platform.

### 1.2 Resource block

A resource block defines the infrastructure object Terraform should create or manage.

```
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"

  tags = {
    Name = "Meridian-VPC"
  }
}
```

There are two important identifiers:

- `aws_vpc` — resource type.
- `main` — Terraform's local resource name.

The resource type determines what kind of object Terraform manages and which arguments are supported.

The local name is used internally by Terraform. It is not automatically the AWS Name tag.

For example:

```
aws_vpc.main.id
```

References the ID of this VPC.

### 1.3 Variable block

Variables make Terraform configurations reusable.

```
variable "environment" {
  type    = string
  default = "dev"
}
```

Reference the variable using:

```
var.environment
```

You can provide different values for development, testing and production without modifying the main resource configuration.

### 1.4 Output block

Outputs expose useful information generated by resources.

```
output "vpc_id" {
  value = aws_vpc.main.id
}
```

After applying the configuration, Terraform displays the VPC ID.

### 1.5 Locals block

Locals define reusable expressions or values inside Terraform configuration.

For example, you can combine project and environment names to create consistent resource names.

```
locals {
  name_prefix = "${var.project_name}-${var.environment}"
}
```

Reference it using:

```
local.name_prefix
```

We will explore this in detail in Section 2.

### 1.6 Data block

A data source reads information about an existing object or information available from an external platform.

For example, instead of hardcoding an AWS AMI ID, Terraform can search for an appropriate Amazon Linux AMI.

We will explore this in Section 3.

## 2. Variables vs Locals — an important interview question

This was one of the major concepts discussed in the session.

Imagine you are creating 100 AWS resources:

- VPC
- Subnets
- EC2 instances
- Load balancers
- Security groups

You want all these resources to follow a naming convention.

For example:

```
ecommerce-dev-vpc
ecommerce-dev-subnet
ecommerce-dev-instance
ecommerce-dev-load-balancer
```

You could define every resource name separately in a `.tfvars` file, but maintaining hundreds of values would become difficult.

Instead, define only the project and environment as variables and use locals to construct reusable names.

### 2.1 Using variables

`variables.tf`

```
variable "project_name" {
  type    = string
  default = "ecommerce"
}

variable "environment" {
  type    = string
  default = "dev"
}
```

These are user-provided inputs.

You can change the values through:

- Default values.
- `.tfvars` files.
- Command-line arguments.
- Environment variables.

### 2.2 Using locals

`locals.tf`

```
locals {
  name_prefix = "${var.project_name}-${var.environment}"
}
```

Now use the local in different resources:

```
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"

  tags = {
    Name = "${local.name_prefix}-vpc"
  }
}

resource "aws_subnet" "public" {
  vpc_id     = aws_vpc.main.id
  cidr_block = "10.0.1.0/24"

  tags = {
    Name = "${local.name_prefix}-public-subnet"
  }
}
```

If the variables are:

```
project_name = ecommerce
environment  = dev
```

The resulting names are:

```
ecommerce-dev-vpc
ecommerce-dev-public-subnet
```

Now change the environment to production:

```
environment = prod
```

The resulting names automatically become:

```
ecommerce-prod-vpc
ecommerce-prod-public-subnet
```

You do not need to change the resource blocks.

### 2.3 Locals can also define common tags

Another useful example from the session is defining common tags once and reusing them across resources.

```
locals {
  common_tags = {
    Project     = var.project_name
    Environment = var.environment
    ManagedBy   = "Terraform"
  }
}
```

Use them in a resource:

```
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"

  tags = merge(local.common_tags, {
    Name = "${local.name_prefix}-vpc"
  })
}
```

This avoids repeating the same tags in every resource.

### 2.4 Variables vs Locals

| Feature                              | Variables                                            | Locals                                             |
| ------------------------------------ | ---------------------------------------------------- | -------------------------------------------------- |
| Purpose                              | Accept external input                                | Define reusable internal values and expressions    |
| Reference                            | `var.name`                                           | `local.name`                                       |
| Can be overridden through `.tfvars`? | Yes                                                  | No                                                 |
| Can be passed using CLI `-var`?      | Yes                                                  | No                                                 |
| Can have default values?             | Yes                                                  | Locals are expressions, not input declarations     |
| Can reference other variables?       | In expressions, but not in their own `default` value | Yes                                                |
| Can reference resource attributes?   | Not in variable defaults                             | Yes                                                |
| Common use                           | Region, environment, instance type                   | Naming conventions, common tags, calculated values |

Interview takeaway

Variables are inputs; locals are internal reusable expressions.

One important clarification: locals are not necessarily derived from variables. A local can also be a fixed value.

For example:

```
locals {
  company_name = "Meridian"
}
```

This local does not depend on any variable.

## 3. Data sources — fetching existing information

This is another important interview topic.

Suppose you want to create an EC2 instance using Amazon Linux 2023.

AWS provides AMI IDs, but those IDs can differ by region and change as new images become available.

Instead of hardcoding an AMI ID, you can use a Terraform data source to look up an appropriate image.

### 3.1 Data source example — AWS AMI

```
data "aws_ami" "amazon_linux" {
  most_recent = true
  owners      = ["amazon"]

  filter {
    name   = "name"
    values = ["al2023-ami-*-x86_64"]
  }
}
```

Let's understand the configuration:

| Argument       | Purpose                                           |
| -------------- | ------------------------------------------------- |
| `data`         | Declares a data source                            |
| `aws_ami`      | AWS AMI data source type                          |
| `amazon_linux` | Terraform's local data source name                |
| `most_recent`  | Selects the most recent matching image            |
| `owners`       | Restricts the search to the specified image owner |
| `filter`       | Defines search criteria                           |

Reference the returned AMI ID:

```
data.aws_ami.amazon_linux.id
```

### 3.2 Use the data source in an EC2 resource

```
resource "aws_instance" "web" {
  ami           = data.aws_ami.amazon_linux.id
  instance_type = "t3.micro"

  tags = {
    Name = "Meridian-Web-Server"
  }
}
```

Terraform first looks up the matching AMI and then uses its ID when creating the EC2 instance.

### 3.3 Resource vs Data source

| Resource                          | Data source                                                                    |
| --------------------------------- | ------------------------------------------------------------------------------ |
| Creates or manages infrastructure | Reads information about existing or externally available infrastructure        |
| Uses `resource` block             | Uses `data` block                                                              |
| Terraform manages its lifecycle   | Terraform does not manage the lifecycle of the object through that data source |
| Example: create a VPC             | Example: look up an existing VPC                                               |

Example from real DevOps work:

You may already have a shared VPC created by a networking team. Your application team needs to create EC2 instances inside that VPC.

You can use a VPC data source to look up its ID instead of creating another VPC.

```
data "aws_vpc" "existing" {
  id = "vpc-0123456789abcdef0"
}
```

Then:

```
resource "aws_subnet" "app_subnet" {
  vpc_id     = data.aws_vpc.existing.id
  cidr_block = "10.0.5.0/24"
}
```

Important: Data sources are not limited to values that change frequently. They are used whenever you need to read information from an external system or existing infrastructure.

## 4. Resource block structure

The instructor then moved into the most important Terraform component: the resource block.

General syntax:

```
resource "<RESOURCE_TYPE>" "<LOCAL_NAME>" {
  argument1 = "value"
  argument2 = "value"
}
```

Example:

```
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}
```

| Component     | Meaning                    |
| ------------- | -------------------------- |
| `resource`    | Declares a resource block  |
| `aws_vpc`     | Resource type              |
| `main`        | Terraform local name       |
| `cidr_block`  | Resource-specific argument |
| `10.0.0.0/16` | Argument value             |

The resource type determines which arguments are valid.

For example:

- AWS VPC has arguments related to CIDR, DNS support and tags.
- AWS EC2 has arguments related to AMI, instance type and subnet.
- AWS S3 bucket has arguments related to bucket configuration.

You do not need to memorize every argument. Use provider documentation to identify the supported arguments and required configuration.

### Where to find resource documentation

[Terraform AWS Provider documentation](https://registry.terraform.io/providers/hashicorp/aws/latest/docs?utm_source=chatgpt.com)

For example, if you want to create an S3 bucket:

1. Open AWS provider documentation.
2. Search for `aws_s3_bucket`.
3. Review the resource arguments.
4. Review the example configuration.
5. Add the required arguments to your Terraform resource block.

## 5. Resource-specific arguments vs Terraform meta-arguments

The instructor introduced two categories of arguments.

### 5.1 Resource-specific arguments

These arguments are specific to the resource type.

For example:

```
resource "aws_instance" "web" {
  ami           = "ami-xxxxxxxx"
  instance_type = "t3.micro"
}
```

Here, `ami` and `instance_type` are EC2 resource arguments.

A VPC resource has a different set of arguments.

### 5.2 Terraform meta-arguments

Meta-arguments control how Terraform manages resources rather than describing only the underlying cloud service.

Some important examples:

| Meta-argument | Purpose                                      |
| ------------- | -------------------------------------------- |
| `count`       | Create multiple instances of a resource      |
| `for_each`    | Create multiple instances using a map or set |
| `depends_on`  | Declare explicit dependencies                |
| `provider`    | Select a provider configuration              |
| `lifecycle`   | Control resource lifecycle behavior          |

These are not specific to AWS VPC or EC2. They are Terraform features.

Important distinction: `provisioner` and `connection` are separate nested blocks, not resource meta-arguments in the same category as `count` or `depends_on`.&#x20;

## 6. Count meta-argument

The `count` meta-argument allows Terraform to create multiple instances of the same resource block.

Example:

```
resource "aws_s3_bucket" "app_bucket" {
  count  = 3
  bucket = "meridian-app-bucket-${count.index}"
}
```

This creates three S3 buckets.

Terraform identifies them using indexes:

```
aws_s3_bucket.app_bucket[0]
aws_s3_bucket.app_bucket[1]
aws_s3_bucket.app_bucket[2]
```

### 6.1 Understanding `count.index`

`count.index` starts from zero.

| count.index | Resource address | Example bucket name     |
| ----------- | ---------------- | ----------------------- |
| 0           | `app_bucket[0]`  | `meridian-app-bucket-0` |
| 1           | `app_bucket[1]`  | `meridian-app-bucket-1` |
| 2           | `app_bucket[2]`  | `meridian-app-bucket-2` |

If you change:

```
count = 3
```

to:

```
count = 10
```

Terraform plans to create seven additional instances, assuming the existing instances remain valid and unchanged.

### 6.2 Using count with outputs

You can retrieve the ARN of a specific bucket:

```
output "first_bucket_arn" {
  value = aws_s3_bucket.app_bucket[0].arn
}
```

To retrieve all bucket ARNs:

```
output "all_bucket_arns" {
  value = aws_s3_bucket.app_bucket[*].arn
}
```

The `[*]` expression collects the corresponding attribute from every instance.

### 6.3 When should we use count?

Use `count` when you want multiple instances of a resource that have essentially the same configuration.

For example:

- Create three identical S3 buckets with generated names.
- Create five identical EC2 instances in the same subnet.
- Create multiple similar security group rules.

Important clarification: `count` instances can still vary using `count.index` and expressions. They do not have to be absolutely identical in every argument. However, `count` is best when instances are largely interchangeable and index-based identity is appropriate.

### 6.4 A production consideration

Suppose you create five EC2 instances using `count`, and later reduce the count to three.

Terraform removes the instances with the highest indexes.

This index-based identity can be inconvenient if each instance represents a distinct application or environment.

That is one reason `for_each` is useful.&#x20;

## 7. Count vs For_each

Both are used to create multiple resources, but they are useful in different scenarios.

Imagine you have three subnets:

```
subnet-a
subnet-b
subnet-c
```

You want to create three EC2 instances, each in a different subnet.

You could use `for_each` to associate each instance with a meaningful key and subnet value.

| Count                                        | For_each                                                        |
| -------------------------------------------- | --------------------------------------------------------------- |
| Uses a numeric index                         | Uses a map key or set element                                   |
| Instances addressed as `[0]`, `[1]`          | Instances addressed using keys                                  |
| Useful for similar interchangeable resources | Useful for resources with distinct identities or configurations |
| Changing list positions can affect identity  | Stable keys help preserve identity                              |

Example of `count`:

```
resource "aws_instance" "web" {
  count         = 3
  ami           = "ami-xxxxxxxx"
  instance_type = "t3.micro"
}
```

Example of `for_each`:

```
variable "subnets" {
  type = map(string)

  default = {
    app-a = "subnet-11111111"
    app-b = "subnet-22222222"
    app-c = "subnet-33333333"
  }
}

resource "aws_instance" "web" {
  for_each      = var.subnets
  ami           = "ami-xxxxxxxx"
  instance_type = "t3.micro"
  subnet_id     = each.value

  tags = {
    Name = each.key
  }
}
```

Terraform creates:

```
aws_instance.web["app-a"]
aws_instance.web["app-b"]
aws_instance.web["app-c"]
```

Here:

- `each.key` is the map key.
- `each.value` is the corresponding subnet ID.

Important: You cannot use `count` and `for_each` together in the same resource or module block.

The instructor indicated that `for_each` would be explored in more detail in the next class.&#x20;

## 8. depends_on — explicit dependencies

Terraform automatically identifies dependencies when one resource references another.

This is called an implicit dependency.

Example:

```
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}

resource "aws_subnet" "public" {
  vpc_id     = aws_vpc.main.id
  cidr_block = "10.0.1.0/24"
}
```

Terraform understands that the subnet requires the VPC ID.

Therefore, it creates the VPC first.

### Explicit dependency

Sometimes resources do not have a direct attribute reference, but you still need to enforce an order.

Example: You want an S3 bucket created before an EC2 instance.

```
resource "aws_s3_bucket" "app" {
  bucket = "meridian-app-example-12345"
}

resource "aws_instance" "web" {
  ami           = "ami-xxxxxxxx"
  instance_type = "t3.micro"

  depends_on = [
    aws_s3_bucket.app
  ]
}
```

Now Terraform knows that the EC2 instance depends on the bucket.

### Implicit vs Explicit dependency

| Implicit                                   | Explicit                            |
| ------------------------------------------ | ----------------------------------- |
| Terraform automatically detects dependency | Engineer specifies dependency       |
| Uses resource references                   | Uses `depends_on`                   |
| Example: subnet references VPC ID          | Example: EC2 waits for an S3 bucket |

Best practice: Prefer implicit dependencies when possible. Use `depends_on` when a real dependency exists but cannot be expressed through an attribute reference.&#x20;

## 9. Lifecycle meta-argument

The `lifecycle` block controls how Terraform handles resource creation, updates and destruction.

Example:

```
resource "aws_instance" "web" {
  ami           = "ami-xxxxxxxx"
  instance_type = "t3.micro"

  lifecycle {
    create_before_destroy = true
  }
}
```

The session covered several lifecycle rules.

### 9.1 create_before_destroy

Normally, when a resource requires replacement, Terraform may destroy the old resource before creating the new one.

With:

```
lifecycle {
  create_before_destroy = true
}
```

Terraform creates the replacement first and destroys the old resource afterwards.

Practical example: You want to replace a server without creating an unnecessary service interruption.

However, this depends on the resource supporting coexistence of old and new instances. Unique names or provider constraints can prevent this strategy from working as expected.

### 9.2 prevent_destroy

```
lifecycle {
  prevent_destroy = true
}
```

This tells Terraform to reject plans that would destroy the resource while this lifecycle rule remains in its configuration.

Example use cases:

- Production databases.
- Important storage resources.
- Critical infrastructure.

Interview question: Why might `terraform destroy` fail?

One possible reason is that a resource has `prevent_destroy = true`.

Important limitation: `prevent_destroy` is not an absolute deletion protection mechanism. If the resource block itself is removed from the configuration, the lifecycle rule is removed too, so this setting does not protect against that deletion path. Use cloud-side deletion protection and backups for stronger safeguards.

### 9.3 ignore_changes

```
lifecycle {
  ignore_changes = [
    tags
  ]
}
```

This tells Terraform to ignore changes to the specified attributes when planning updates.

Example:

- Terraform creates an EC2 instance.
- Another approved process updates its tags.
- You do not want Terraform to revert those tag changes during the next apply.

You can use `ignore_changes` for selected attributes.

Avoid ignoring attributes without a clear reason, because Terraform may stop correcting configuration drift for those attributes.

### 9.4 replace_triggered_by

This lifecycle rule forces a resource to be replaced when a referenced resource or resource attribute changes.

Example:

```
lifecycle {
  replace_triggered_by = [
    aws_instance.app.ami
  ]
}
```

This is useful when a resource must be replaced because another managed resource has changed.

### 9.5 Preconditions and postconditions

These allow you to define conditions that Terraform must evaluate.

Precondition: Checked before the relevant operation proceeds.

Postcondition: Checked after the relevant operation.

Example:

```
resource "aws_instance" "web" {
  ami           = data.aws_ami.amazon_linux.id
  instance_type = "t3.micro"

  lifecycle {
    precondition {
      condition     = data.aws_ami.amazon_linux.architecture == "x86_64"
      error_message = "The selected AMI must use x86_64 architecture."
    }
  }
}
```

This checks that the selected AMI has the expected architecture.

### Lifecycle summary

| Rule                    | Purpose                                                    |
| ----------------------- | ---------------------------------------------------------- |
| `create_before_destroy` | Create replacement before destroying old resource          |
| `prevent_destroy`       | Reject destruction while rule remains configured           |
| `ignore_changes`        | Ignore selected attribute changes                          |
| `replace_triggered_by`  | Trigger replacement based on another resource or attribute |
| `precondition`          | Check a condition before an operation                      |
| `postcondition`         | Check a condition after an operation                       |

## 10. Provisioners in Terraform

The instructor then explained provisioners and their relationship to configuration management tools such as Ansible.

Terraform is primarily an infrastructure provisioning tool.

For example, Terraform can create an EC2 instance, VPC, subnet and security group.

But what if you want to execute commands on the newly created EC2 instance?

This is where provisioners can help.

A provisioner executes an action on the local machine or a remote resource as part of a Terraform operation.

### 10.1 Three types of provisioners

| Provisioner   | Where does it execute?            | Purpose                               |
| ------------- | --------------------------------- | ------------------------------------- |
| `local-exec`  | Machine running Terraform         | Executes a local command              |
| `remote-exec` | Remote resource                   | Executes commands on a remote machine |
| `file`        | Copies files to a remote resource | Transfers files or directories        |

### 10.2 local-exec

Executes a command on the machine where Terraform is running.

Example:

```
resource "aws_instance" "web" {
  ami           = "ami-xxxxxxxx"
  instance_type = "t3.micro"

  provisioner "local-exec" {
    command = "echo EC2 instance created"
  }
}
```

When Terraform creates the resource, it executes the local command.

Use cases:

- Running local scripts.
- Triggering external CLI commands.
- Writing information to local files.
- Sending notifications.

### 10.3 remote-exec

Executes commands on a remote resource, such as an EC2 instance.

Example:

```
resource "aws_instance" "web" {
  ami           = "ami-xxxxxxxx"
  instance_type = "t3.micro"

  provisioner "remote-exec" {
    inline = [
      "sudo dnf update -y",
      "sudo dnf install nginx -y",
      "sudo systemctl enable --now nginx"
    ]

    connection {
      type        = "ssh"
      user        = "ec2-user"
      private_key = file("~/.ssh/id_ed25519")
      host        = self.public_ip
    }
  }
}
```

Here:

- Terraform creates the EC2 instance.
- The connection block specifies how to connect.
- SSH is used to reach the remote instance.
- `remote-exec` executes the commands on that instance.

Important: The instance must be reachable, SSH must be permitted, and the connection credentials must work.

### 10.4 file provisioner

Copies a file from the Terraform machine to a remote resource.

Example:

```
resource "aws_instance" "web" {
  ami           = "ami-xxxxxxxx"
  instance_type = "t3.micro"

  provisioner "file" {
    source      = "app.conf"
    destination = "/tmp/app.conf"

    connection {
      type        = "ssh"
      user        = "ec2-user"
      private_key = file("~/.ssh/id_ed25519")
      host        = self.public_ip
    }
  }
}
```

This copies `app.conf` from the local Terraform machine to `/tmp/app.conf` on the EC2 instance.

### 10.5 local-exec vs remote-exec

## Where does the command execute?

local-exec

Terraform host

Local

remote-exec

Created remote server

Remote

Example:

- `local-exec`: Run a script on your EC2 management machine.
- `remote-exec`: Install NGINX on the newly created EC2 instance.

### 10.6 When should we use provisioners?

Last resort

Terraform documentation recommends treating provisioners as a last resort.

Why?

- They are harder to make predictable and repeatable.
- Terraform cannot fully model the effects of arbitrary commands.
- A failed provisioner can leave a partially configured resource.
- Retrying and recovering from failures can be difficult.

Prefer alternatives such as:

- EC2 user data or cloud-init.
- Ansible.
- Configuration management tools.
- Container images.
- Cloud-native deployment mechanisms.

Practical DevOps example: Rather than creating an EC2 instance and installing every application package through `remote-exec`, you could prepare an image with the required software already installed or use Ansible for configuration management.

## 11. Provisioner execution timing

Provisioners normally run during resource creation.

You can also configure a destroy-time provisioner.

Example:

```
resource "aws_instance" "web" {
  ami           = "ami-xxxxxxxx"
  instance_type = "t3.micro"

  provisioner "local-exec" {
    when    = destroy
    command = "echo EC2 instance is being destroyed"
  }
}
```

Here:

```
when = destroy
```

means that the provisioner runs during the destruction of the resource.

If you omit `when`, the default behavior is creation-time execution.

Important: Destroy-time provisioners have limitations. They do not run in every possible removal scenario, including when the resource block is removed from configuration or when the resource is tainted. Do not rely on them as your only cleanup or backup mechanism.&#x20;

## 12. Terraform is a DSL, not a general-purpose programming language

The instructor concluded by explaining that Terraform uses HCL, a domain-specific language (DSL).

A DSL is designed for a specific purpose.

For example:

| Language      | Main purpose                      |
| ------------- | --------------------------------- |
| Python        | General-purpose programming       |
| Java          | General-purpose programming       |
| Terraform HCL | Infrastructure configuration      |
| SQL           | Working with relational databases |
| HTML          | Structuring web content           |

Terraform HCL is designed to describe infrastructure and its configuration.

It supports expressions, variables, functions, conditions, loops and reusable modules, but it is not intended to replace general-purpose programming languages.

Remember: You use Terraform to describe and manage infrastructure, not to build every type of application.&#x20;

## 13. Complete example — combining the concepts

This example brings together variables, locals, data sources, resources and outputs.

```

# variables.tf

variable "project_name" {
  type    = string
  default = "meridian"
}

variable "environment" {
  type    = string
  default = "dev"
}

variable "instance_type" {
  type    = string
  default = "t3.micro"
}

variable "vpc_cidr" {
  type    = string
  default = "10.0.0.0/16"
}

```

```

# locals.tf

locals {
  name_prefix = "${var.project_name}-${var.environment}"

  common_tags = {
    Project     = var.project_name
    Environment = var.environment
    ManagedBy   = "Terraform"
  }
}

```

```

# data.tf

data "aws_ami" "amazon_linux" {
  most_recent = true
  owners      = ["amazon"]

  filter {
    name   = "name"
    values = ["al2023-ami-*-x86_64"]
  }
}

```

```

# main.tf

provider "aws" {
  region = "ap-south-1"
}

resource "aws_vpc" "main" {
  cidr_block = var.vpc_cidr

  tags = merge(local.common_tags, {
    Name = "${local.name_prefix}-vpc"
  })
}

resource "aws_instance" "web" {
  ami           = data.aws_ami.amazon_linux.id
  instance_type = var.instance_type

  tags = merge(local.common_tags, {
    Name = "${local.name_prefix}-web"
  })
}

```

```

# outputs.tf

output "vpc_id" {
  value = aws_vpc.main.id
}

output "instance_id" {
  value = aws_instance.web.id
}

output "instance_public_ip" {
  value = aws_instance.web.public_ip
}

```

The example demonstrates:

1. Variables accept project-specific values.
2. Locals generate reusable names and tags.
3. Data sources look up the latest matching Amazon Linux AMI.
4. Resources create the VPC and EC2 instance.
5. Outputs display useful infrastructure information.

Note: This is a learning example, not a complete production network design. The EC2 instance is not explicitly attached to the VPC because the subnet and networking configuration have not been added.

## 14. Interview questions and answers

1\. What is the difference between a variable and a local in Terraform?

Variables accept external input values. Locals define internal reusable expressions or values that can be referenced throughout the configuration.

2\. What is a data source in Terraform?

A data source retrieves information about existing infrastructure or information available from an external platform without managing that object's lifecycle through the data source.

3\. What is the difference between a resource and a data source?

A resource creates or manages infrastructure. A data source reads information about an existing or externally available object.

4\. What is a meta-argument?

A Terraform-specific argument that controls how Terraform manages a resource, such as `count`, `for_each`, `depends_on` and `lifecycle`.

5\. What is the difference between count and for_each?

`count` creates indexed instances. `for_each` creates instances identified by map keys or set elements. `for_each` is useful when instances have distinct identities or configurations.

6\. Can we use count and for_each together?

No. A resource or module block can use one or the other, not both.

7\. What is depends_on?

It explicitly defines a dependency when Terraform cannot infer the required ordering from resource references.

8\. What is prevent_destroy?

A lifecycle rule that makes Terraform reject destruction of a resource while the rule remains configured.

9\. What is ignore_changes?

A lifecycle rule that tells Terraform to ignore changes to specified resource attributes during planning.

10\. What is create_before_destroy?

It instructs Terraform to create a replacement resource before destroying the existing resource.

11\. What are Terraform provisioners?

Provisioners execute commands or copy files locally or on remote resources as part of resource operations.

12\. What is the difference between local-exec and remote-exec?

`local-exec` runs on the machine executing Terraform. `remote-exec` runs on the remote resource.

13\. Why are provisioners considered a last resort?

Because arbitrary commands are difficult for Terraform to model and recover from reliably. Dedicated configuration management or image-building tools are usually better.

14\. What is a Terraform DSL?

A domain-specific language designed for a particular purpose. HCL is used to describe infrastructure configuration.
